# Бриф на дизайн: панель установки Argon (self-hosted)

Это задание для дизайнера. Всё техническое ниже — не пожелания, а то, что сервер уже отдаёт и принимает;
контракты сняты с кода, а не придуманы. Тексты интерфейса — **на английском** (продукт англоязычный),
сам бриф на русском, чтобы его было удобно править.

---

## 1. Что это за продукт и кто перед экраном

Argon — чат-платформа (голос, каналы, пространства). Есть облачная версия и **self-hosted**: человек
ставит её себе на сервер.

Установка выглядит так. Оператор заходит по SSH на пустую машину и запускает одну команду. Скрипт
проверяет машину, спрашивает домен и как до сервера будет доходить трафик, поднимает Traefik и за ним —
контейнер-панель, и печатает в терминал **адрес и код**:

```
  Open   https://chat.example.org/panel
  Code   K7M2-PQ4X-9JHN-3TWD
```

Дальше человек открывает браузер, вводит код и доводит установку до конца **уже в этом интерфейсе**.
Его и нужно нарисовать.

**Кто это.** Системный администратор или разработчик. Он только что работал в терминале, он понимает
слова «контейнер», «сертификат», «S3-бакет». Ему **не нужно** ободрение, иллюстрации и объяснение, что
такое чат. Ему нужно: видеть, что происходит; понимать, что уже сделано, а что нет; и не остаться один
на один с непонятной ошибкой на чужом сервере.

**Тон.** Это инструмент, а не онбординг. Плотно, спокойно, без восклицаний. Ближе к панели облачного
провайдера, чем к мастеру установки приложения.

**Важно про длительность.** Установка занимает **минуты**: скачиваются образы, поднимается база,
Argon стартует. Экран ожидания здесь — не спиннер на две секунды, а полноценный экран с логом.

---

## 2. Жёсткие ограничения — прочитать до того, как рисовать

Эти четыре пункта меняют структуру макетов, а не только детали.

**Всё состояние живёт на сервере.** Клиент не хранит прогресс мастера. Любой экран должен полностью
восстанавливаться из одного `GET /api/state`. Человек может закрыть вкладку посреди установки, уйти,
вернуться через час с другого компьютера — и должен увидеть ровно то место, где всё находится. Значит:
никаких «шагов», которые существуют только во фронтенде, и никакого мастера, который при перезагрузке
начинается сначала.

**Страница отдаётся по двум адресам сразу** — `/` и `/panel` (второй с обрезкой префикса на прокси).
Все пути к ресурсам должны быть **относительными**. Роутинг — либо по хешу, либо такой, который
переживает F5 на любом из двух базовых путей.

**Никакого интернета.** Страницу отдаёт контейнер на сервере, который может стоять за файрволом без
доступа наружу. Ни CDN, ни Google Fonts, ни внешних скриптов и иконок — всё встроено. Шрифты либо
системные, либо зашитые в страницу.

**Тёмная и светлая темы.** Обе. Оператор в терминале в три часа ночи и оператор в офисе — оба реальны.

Дополнительно: основной сценарий — десктоп, но на телефоне не должно ломаться (код с экрана сервера
переписывают руками, иногда с телефона в руке).

---

## 3. Что нужно на выходе

**Интерактивный кликабельный прототип**, а не статичные картинки. Конкретно:

- по нему можно пройти весь путь: вход по коду → вопросы → запуск → результат;
- переключаются **все** состояния, включая неуспешные (их ниже пять штук, и они важнее удачного пути);
- видно поведение: наведение, фокус, заблокированные кнопки, поля с ошибкой, обратный отсчёт блокировки,
  «лог едет», индикатор ожидания;
- обе темы переключаются;
- есть состояния пустоты и загрузки, а не только «данные уже пришли».

Плюс к прототипу: короткий разбор решений — почему такая плотность, где что находится в иерархии,
как ведёт себя длинный текст.

## 4. Экраны

### 4.1. Вход по коду

Единственная преграда. Кода нет ни в письме, ни в базе — он напечатан в терминале того человека,
который запустил установку. Это и есть доказательство, что за экраном — владелец машины.

Формат: **четыре группы по четыре символа**, алфавит `A–Z` и `2–9` без похожих глифов (нет `I`, `O`,
`0`, `1`). Пример: `K7M2-PQ4X-9JHN-3TWD`.

Что должно быть учтено:

- код переписывают **руками с другого экрана**, иногда с фотографии. Поле ввода должно этому помогать:
  крупный моноширинный шрифт, разделение на группы, вставка целиком из буфера должна работать;
- **пять неверных попыток — блокировка на 30 секунд**. Это нужно показать честно: сколько осталось,
  и что после можно снова;
- **challenge живёт 2 минуты**. Если человек ушёл и вернулся, попытка отвалится как просроченная —
  это не ошибка ввода, и звучать должно иначе;
- когда установка уже завершена, вход по коду отключается навсегда (`410`) — нужен отдельный экран
  «этот код больше не работает, установка завершена».

Ошибки, которые надо развести визуально: неверный код · попытка просрочена · заблокировано на N секунд ·
установка уже завершена.

### 4.2. Вопросы

Их шесть. Сколько экранов — решать вам: можно по одному, можно сгруппировать. Сервер к этому равнодушен,
он принимает любое подмножество за раз и сам говорит, чего ещё не хватает (поле `missing`).

| Ответ | Что это | Тонкость |
|---|---|---|
| `domain` | имя, по которому отвечает инстанс | **уже введён в терминале** — показывать как подтверждение, а не как новый вопрос |
| `traffic` | как трафик доходит: свой сертификат / за прокси Cloudflare / туннель Cloudflare / Let's Encrypt | **тоже уже выбран в терминале** — то же самое |
| `serverVersion` | версия Argon или закреплённая ссылка на образ | запускает долгую операцию, см. ниже |
| `roles` | какие части сервера запускать | список приходит с сервера |
| `storage` | где лежат файлы: встроенное хранилище или внешний S3 | есть секреты, см. ниже |
| `voice` | нужен ли голос | влияет на предупреждения |

**Версия — это не просто поле.** После ввода запускается `POST /api/setup/interrogate`: сервер
**запускает контейнер с образом Argon и спрашивает его, что он умеет**. Это до минуты. Только после
этого известны роли и топологии, то есть следующий вопрос буквально нельзя задать раньше. Нужно
состояние ожидания с внятным объяснением, что происходит, — иначе это выглядит как зависшая форма.

Результат опроса может прийти с оговоркой (`pairing`): образ **слишком старый**, **слишком новый** или
**не говорит свою версию**. Это не отказ — установка продолжается, но с предупреждением, и текст
предупреждения приходит с сервера готовым предложением.

**Роли.** Приходят от образа списком, у каждой: идентификатор, тип (`silo` или `client`), сколько
внутри грейнов, сколько фич, и описание одной строкой. Пять ролей **обязательны и не выключаются**
(`entrypoint`, `aegis`, `core`, `media`, `jobs`), четыре опциональны (`voice`, `botapi`, `admin`,
`account`). Разница между «обязательно» и «выбрано» должна читаться с одного взгляда — это не одинаковые
галочки.

**Хранилище.** Либо встроенное (ничего не спрашиваем), либо внешний S3: endpoint, bucket, region и пара
ключей. Ключи — **односторонние**: сервер их принимает и больше никогда не отдаёт. В состоянии
возвращается только список названий тех секретов, которые у него есть. Значит поле после сохранения не
показывает значение, а показывает «задан» с возможностью заменить. Это надо нарисовать, а не оставить
пустым полем, которое выглядит как несохранённое.

**Как отвечает сервер на ответ.** Либо всё состояние заново, либо `400` со списком
`{ field, problem }` — по одному предложению на каждое отвергнутое поле. Предложения **длинные и
человеческие**, не «invalid input». Место под ошибку рядом с полем должно вмещать две строки.

### 4.3. Предупреждения

Отдельная сущность, и её легко испортить. Это **не ошибки** — они ничего не блокируют, но каждое
описывает способ, которым инстанс тихо окажется сломанным. Формат — готовые абзацы от сервера, по 200–400
знаков. Например (это настоящий текст, не пример-заглушка):

> whoever follows a file link has to be able to read that bucket, and this installer cannot make it so.
> A private bucket produces an instance where everything works except that every avatar and attachment
> is a broken image.

Их может быть от нуля до пяти одновременно. Нужен блок, который держит несколько таких абзацев и при этом
не выглядит как страница ошибки. Компактные «чипы» и однострочные тосты сюда не подойдут — текст в них
не влезет, а сокращать его нельзя, в нём вся ценность.

### 4.4. Проверка перед запуском

Состояние `ready`: всё отвечено. Показать сводку ответов, все предупреждения и одну кнопку.

Важно: за этой кнопкой — **первое необратимое действие**. До неё на машине не менялось ничего.

### 4.5. Запуск — экран ожидания

Занимает минуты. Проходит через стадии: `applying` (генерация конфигурации и проверка) → `configured`
(файлы на диске) → `starting` (образы скачиваются, контейнеры поднимаются) → `running`.

Что показывать:

- где мы в этой последовательности;
- **лог** — сервер отдаёт хвост вывода `docker compose`, уже очищенный от секретов, массивом строк.
  Это настоящий технический вывод, моноширинный, его хочется видеть целиком, и он должен ехать;
- по каждому сервису — состояние (`running`, `exited`, `restarting`, `created`), здоровье
  (`healthy`, `starting`, `unhealthy`), код выхода. Сервисов около десяти;
- адрес панели — **сразу, не в конце**. Сервер отдаёт его заранее именно для этого: если браузер устанет
  ждать, человек всё равно знает, куда идти.

### 4.6. Чем всё кончилось — пять исходов

Удачный один, неудачных пять, и они отличаются не текстом, а тем, **что теперь делать**. Это главное,
что должен передать дизайн.

**`running` — получилось.** Адрес панели, что теперь по этому адресу, список записанных файлов (путь и
права доступа), состояние сервисов.

**`invalid` — сервер отказался от конфигурации. На диск не записано ничего.** Возврат бесплатный:
поправить ответ и нажать снова. Приходит отчёт по каждой роли: имя роли, прошла или нет, и **сырой
многострочный вывод проверки** словами самого сервера. Нужен моноширинный блок со скроллом, свёрнутый
по умолчанию для тех ролей, что прошли.

**`start-failed` — запуск сорвался. И это два разных исхода под одним кодом.** В теле ответа приходит
булево `running`, и оно решает всё:

- `running: false` — не успело ничего создать. На машине ничего не запущено, конфигурация лежит на диске,
  повтор бесплатный. По сути то же самое, что `invalid`, только сорвалось на шаг позже.
- `running: true` — **контейнеры уже поднялись**, и инстанс всё равно не работает. Стадия становится
  `degraded`. Это единственный случай, где **повтор не бесплатен**: на машине что-то живёт, и следующее
  действие произойдёт с работающей системой.

Один код ответа, два совершенно разных совета человеку. Если дизайн покажет их одинаково — он покажет их
неправильно; разница между «нажмите ещё раз» и «сначала посмотрите, что там работает» здесь и есть весь
смысл экрана.

**`not-startable` — проект не собрался.** Например, выбран режим за прокси Cloudflare, а сертификата для
машины нет. Ничего не записано, ничего не запущено; отказ приходит одним предложением от сервера.

**`not-ready` — запустилось, но не дождались.** Приходит список тех сервисов, которые так и не
поднялись, поимённо. Не «истекло время ожидания», а «вот эти три».

**`blocked` / `image-unavailable` — не начали.** Что-то на диске делает продолжение небезопасным, либо
образ недоступен. Одно предложение объяснения от сервера.

Отдельно: состояние **`restarted`** — панель нашла на диске установку, которую делала не она. Ответы того
запуска потеряны. Это не ошибка, но человека надо предупредить.

### 4.7. После установки — панель

Тот же контейнер продолжает работать и становится **постоянной панелью управления**: контейнеры, логи,
конфигурация, обновления, резервные копии, срок действия сертификата.

Детальный дизайн панели в это задание не входит. Но нужно показать, **как одно превращается в другое**:
мастер завершился, и по тому же адресу теперь живёт другой инструмент. Достаточно каркаса и навигации.

Одна деталь: после завершения установки код перестаёт работать навсегда. Значит панели нужен настоящий
вход — учётная запись с паролем. Пока его нет; в макете можно обозначить место.

## 5. Контракт API

Всё под сессионной cookie, кроме первых трёх. Ответ на любой шаг — целиком новое состояние.

```
GET  /api/health              → "ok"                    без авторизации
POST /api/auth/challenge      → { id, nonce }           410 если установка завершена
POST /api/auth/verify         { challengeId, proof }    401 неверно · 410 просрочен · 429 блокировка
                              → ставит cookie

GET  /api/state               → SetupState
POST /api/setup/step          Step → SetupState         400 { error:"rejected", rejections:[…] }
POST /api/setup/interrogate   → SetupState              409 несовместимо · 503 образ недоступен
POST /api/setup/apply         → SetupState              400 incomplete   · 422 invalid
                                                        409 blocked      · 409 not-startable
                                                        503 image        · 504 not-ready
                                                        500 start-failed { running: boolean }
```

`proof` — это `HMAC-SHA256(код, nonce)` в hex. Код никогда не уходит на сервер.

Состояние, которое рендерит интерфейс:

```ts
{
  stage: "awaiting-configuration" | "ready" | "applying" | "invalid" | "configured"
       | "starting" | "running" | "degraded" | "blocked" | "unavailable",

  answers:  { domain?, serverVersion?, roles?, storage?, traffic?, voice? },
  missing:  string[],            // какие ответы ещё нужны
  credentials: string[],         // только имена, никогда значения

  image?: {
    reference: string,
    version:   { value, source, reference },
    pairing:   { ok: true } | { ok: false, reason: "too-old"|"too-new"|"unreadable", detail: string },
    roles:      { id, kind: "silo"|"client", grains, features, description }[],
    topologies: { name, roles }[],
  },

  warnings: string[],            // готовые абзацы, 0–5 штук
  restarted: boolean,            // нашли чужую установку
  note?: string,

  written?:    { path, mode }[],
  validation?: { role, ok, output }[],      // output — сырой многострочный вывод
  services?:   { service, state, health?, exitCode? }[],
  progress?:   string[],                    // хвост вывода docker, очищенный
  panel?:      { url, note },
  problem?:    string,
  retired:     boolean,                     // код больше не действует
}
```

## 6. Чего делать не надо

- Не изобретать шаги, которых нет в списке ответов, и не убирать те, что есть.
- Не сокращать тексты предупреждений и ошибок под размер плашки — верстать под текст, а не наоборот.
- Не показывать секреты после сохранения: сервер их не отдаёт, показать нечего.
- Не делать прогресс фальшивым. Реальных стадий четыре, они известны; проценты — нет.
- Не прятать неудачные исходы за общий экран ошибки. Их пять, и они требуют разных действий — а один
  код ответа (`500`) означает сразу два из них, и различает их поле в теле.
- Не рассчитывать на иконочный шрифт или картинки из сети.

## 7. Что стоит спросить, если непонятно

Два места, где мы сами ещё не определились, и мнение дизайнера тут полезно:

1. **Домен и способ доставки трафика уже спрошены в терминале.** Мы можем передать их в панель заранее.
   Тогда это два подтверждения вместо двух вопросов — и, возможно, первый экран становится не первым
   вопросом, а сводкой «вот что мы уже знаем о вашей машине».
2. **Опрос образа занимает до минуты.** Его можно запускать в фоне сразу, как только названа версия,
   пока человек отвечает на следующий вопрос. Тогда ожидание исчезает — но появляется состояние
   «ответ ещё едет», которое надо где-то показать.
