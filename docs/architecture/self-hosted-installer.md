# Self-hosted Argon: the installer

A design for standing up Argon on a machine somebody owns, from one command, without them having to
understand the topology first.

Status: design. Nothing here is built except the preflight script, which exists and is tested. Where a
claim is about someone else's product — Cloudflare, Let's Encrypt — it is marked as verified or as needing
verification, because getting one of those wrong sends the whole flow down a path that cannot work.

---

## 1. What this is

One command on a fresh machine ends with a working Argon instance and a panel the operator can log into.
Between those two points the installer has to answer questions it cannot guess — what the instance is
called, how traffic reaches it, whether storage is local — and it has to answer them **before** the panel
exists, because the panel is served over the very TLS being configured.

That ordering is the whole design. Everything below follows from it.

### What it is not

Not a cluster installer. One machine, one instance. Multi-region is a separate thing and is paused —
see [multi-region-status.md](multi-region-status.md).

Not a Kubernetes chart. The target is somebody with a VPS, not somebody with a platform team.

---

## 2. Shape

```
  ┌─ bootstrap.sh ────────────────────────────────────────────────┐
  │  preflight: machine, tools, network, resources                │
  │  install docker if asked                                      │
  │  ask: domain, and how traffic gets here                       │
  │  pull the bootstrapper image, ask it for the edge's project   │
  │  start Traefik and the panel — the door first, see §10        │
  └───────────────────────────────────────────────────────────────┘
                              │
                              ▼
  ┌─ bootstrapper (container, behind Traefik) ────────────────────┐
  │  serves the setup UI over the TLS Traefik established         │
  │  operator enters the auth code printed in their terminal      │
  │  asks: version, storage, mail, voice, which roles             │
  │  writes conf.d/*.json and the secrets file                    │
  │  validates by asking the server binary                        │
  │  pulls images, starts everything, waits for health            │
  └───────────────────────────────────────────────────────────────┘
                              │
                              ▼
  ┌─ panel ───────────────────────────────────────────────────────┐
  │  the same container, now a control surface: containers,       │
  │  configuration, upgrades, backups, logs                       │
  └───────────────────────────────────────────────────────────────┘
```

The script is deliberately thin. It knows about the machine and about traffic; it knows nothing about
Argon's configuration. Everything that requires knowing what a feature reads happens in the bootstrapper,
which asks the server binary rather than carrying its own copy of that knowledge — see §7.

---

## 3. Preflight

Built. `deploy/selfhosted/preflight.sh`.

Reports on the distribution, the package manager, privilege, the tools it needs, docker and its compose
plugin, the local and public addresses, memory, cores and disk. Installs nothing without printing the
exact command and asking. No terminal means no, so a run from cron or a pipe changes nothing.

Two properties worth keeping when it grows: every external call is announced before it happens, and
nothing is enforced that the operator might know better about. Resource numbers are a shape, not a
specification.

## 4. The auth code

**What it protects.** That the person opening the setup UI is the person who ran the install. Nothing
more. It is not an account, it does not persist into the product, and it stops being interesting the
moment the first operator account exists.

**Where it lives.** Generated by the script, printed to the terminal, and written next to the install
with mode `600`. The operator is looking at it already — they just ran the command.

**How it is exchanged.** Not sent. The UI proves knowledge of it: the server issues a random challenge,
the page returns `HMAC(code, challenge)`, and a session key is derived from the same secret. The code
never crosses the wire, so a stripped or misconfigured TLS layer does not hand it to a listener.

This is cheap and worth doing even though §5 makes the channel trustworthy anyway. What it does **not**
defend against is an active attacker who can rewrite the page delivering that JavaScript — which is why
the channel is established first and the UI second, rather than the other way round.

**Rate limiting and expiry.** The code is short enough to type, which means it is short enough to guess:
attempts must be rate limited, and the code should expire once setup completes. An installer that leaves
a permanently valid bootstrap credential on a public box has replaced one problem with a worse one.

## 5. Traffic and TLS — three paths

**Traefik is the ingress and it terminates TLS.** One machine has one `:443`, and three things want to
be reachable on it — the API and realtime hub, the object store's read path, and the panel — so something
has to route by path. Traefik does that, holds the certificate, and renews it.

Kestrel then serves plain HTTP on the compose network. That is worth stating because an earlier draft of
this document said the opposite: it had Kestrel terminating TLS from a certificate on disk and no proxy
at all, which came from mishearing "Traefik" as a phrase about traffic. Everything downstream of that
mistake — two terminations, an internal hop with certificate verification disabled and a paragraph
explaining why — went away with it.

So all four shapes below end at the same place: Traefik holding a certificate, and one internal network
where nothing is encrypted because nothing leaves the machine.

The script asks for a domain first, then determines which shape applies — two of them can be detected
rather than asked.

Each shape reaches Traefik differently: a certificate on disk goes in through its file provider, and
Let's Encrypt is its own ACME resolver. A combination that matches none of them is a hard failure at
generation time, not an edge that quietly serves plain HTTP.

### Path A — the operator brings their own certificate

For anyone who already has a certificate: a corporate CA, a wildcard they manage, an existing ACME setup
elsewhere on the box. It reaches Traefik through the file provider.

The script tells them where to put the two files and validates what it finds: that the key matches the
certificate, that the certificate covers the domain they entered, and that it has not expired. All three
are cheap and all three are things people get wrong — a chain in the wrong order, a certificate for the
apex when the domain is a subdomain.

**Renewal is theirs.** The installer must say so plainly, and the panel must show the expiry date and warn
before it lapses, because an instance that stops answering in ninety days with no warning is the worst
outcome of this path.

### Path B — the domain is behind Cloudflare

Detected, not asked: resolve the domain and compare the answer against Cloudflare's published proxy
ranges. *(Verify the current endpoint for those ranges before implementing — it is published, but pin the
exact URL at build time rather than trusting this document.)*

**The trap this path has to avoid.** "Behind Cloudflare" does not mean the origin needs no certificate. It
means Cloudflare terminates TLS at its edge and then makes its own connection to the origin, and how that
second connection is secured is a setting on their side:

| Cloudflare mode | Edge → origin | Acceptable here |
|---|---|---|
| Flexible | plaintext HTTP | **No.** Auth tokens and message content in clear across the internet. |
| Full | TLS, certificate not verified | Workable; a self-signed origin certificate is enough. |
| Full (strict) | TLS, certificate verified | Correct, and what the installer should aim for. |

The right answer is a **Cloudflare Origin CA certificate** — free, long-lived, trusted by Cloudflare and
by nothing else, which is exactly the property wanted for an origin. It is generated in the operator's own
Cloudflare dashboard in about a minute.

**We do not ask for an API token.** The installer detects that the domain is proxied, then tells the
operator the two things to do on their side — issue an Origin CA certificate, set the mode to Full
(strict) — and waits for the files, exactly as path A waits for them. Mechanically the two paths converge:
a certificate and a key arrive on disk and Traefik's file provider picks them up.

Not holding a credential to somebody else's DNS is worth more than the automation it would buy. The
installer would need it once, at setup, and would then either keep it — a token to the operator's whole
zone, sitting on a box — or discard it and be unable to renew. An Origin CA certificate lasts years, so
there is nothing to renew anyway.

#### B2 — Cloudflare Tunnel

A sub-path, and for a machine behind NAT it is the best answer available: the tunnel makes an **outbound**
connection, so no port is forwarded, no inbound firewall rule exists, and the origin needs no certificate
at all because the tunnel carries the TLS.

Chosen when the machine has no public address, or when the operator prefers not to expose one. It costs a
long-lived credential on the box and a dependency on Cloudflare being up.

#### ⚠ Voice does not go through the Cloudflare proxy

**This is the most important sentence in this document.** Cloudflare's HTTP proxy carries HTTP and
WebSockets. It does not carry arbitrary UDP, and real-time media is UDP. A Cloudflare-proxied Argon has
working chat and **broken voice** unless media is given a path of its own.

So path B is not one decision but two, and the installer asks about voice *before* settling it. The
question put to the operator is where LiveKit lives, and it is theirs to answer because the answer depends
on what their Cloudflare account can do — which they know and we do not:

**Behind the proxy, on the domain already entered.** The right choice if their plan carries the traffic
the HTTP proxy will not. Nothing extra is published and there is one hostname. If it turns out their plan
does not, voice does not work and they change this answer — which is why it is a question and not a
detection: guessing wrong on their behalf produces the same broken instance with none of the explanation.

**Directly, on a second subdomain.** Published DNS-only ("grey cloud"), pointing straight at the machine.
Cloudflare is not in that path at all, which is the point: the media endpoint is reached directly and
carries its own traffic.

The installer prints the exact record to create — name, type, address, grey cloud — and then **verifies**
it: resolves the name, checks it answers with this machine's address and not a Cloudflare one. Creating it
would need the token this design does not take; checking it needs nothing, and catches the orange cloud
left on by accident, which is the mistake that makes voice fail silently.

That second answer has a consequence worth stating, because it is easy to design past. A Cloudflare
instance with voice published directly ends up running **two TLS paths at once**: an Origin CA certificate
for the proxied hostname, and — for the media subdomain, which Cloudflare never sees — an ordinary
certificate obtained the way path A or path C would obtain one. They are not alternatives on that machine;
they are both present, with different renewal stories and different expiry dates. The panel has to show
both.

What the installer must not do is present a configuration in which voice is silently dead. An operator
discovering that after inviting their users is the failure mode this section exists to prevent.

*(Verify before implementing: current Cloudflare WebSocket idle timeouts, and whether they interact badly
with the hub's own keep-alive. A proxy that closes idle sockets at a shorter interval than the client
reconnect logic expects produces reconnect storms that look like a server fault.)*

### Path C — Let's Encrypt, obtained by Traefik

For a machine with a public address and no Cloudflare.

HTTP-01 needs port 80 reachable from the internet; TLS-ALPN-01 needs 443. The script already knows
whether the machine has a public address, and should verify reachability rather than infer it — a VPS
with a provider firewall in front looks public and is not.

If neither port is reachable, this path cannot work and the script must say which of the other two to
take rather than retrying.

**Renewal is Traefik's**, and this is where the ingress pays for itself. The earlier draft had to
explain how a rotated certificate reaches a running Kestrel — it reads the file when the listener is
built, so nothing happens until a restart or a re-reading callback, and a self-hosted instance that drops
every websocket every sixty days is a poor experience. None of that exists now: the renewal happens in
the component holding the certificate, and no Argon process learns about it.

### Choosing

```
domain entered
  ├─ resolves into Cloudflare ranges ──────────► B  (+ ask about voice)
  ├─ no public address ────────────────────────► B2 (tunnel) or A
  ├─ :80 or :443 reachable from outside ───────► C
  └─ otherwise ────────────────────────────────► A, with an explanation
```

Detected where possible, asked where not, and every branch ends able to state why it was chosen.

## 6. What actually runs

Argon is not one image. A working instance is the server plus its dependencies, and the installer should
say so before it starts pulling: first run is minutes, not seconds.

**Roles.** The installer starts the roles the instance needs, the same ones a real deployment runs, on
one machine. Not the single-process `dev` role: that is a configuration which exists nowhere else, so it
breaks in ways production never sees and gets fixed last.

Which ones depends on what the operator wants. Some exist for a business a self-hosted instance does not
have, and each one skipped is a container not run and a configuration section not asked about:

| Role | Self-hosted | Why |
|---|---|---|
| `entrypoint` | required | the API and the realtime hub |
| `aegis` | required | sign-in; without it nobody gets in |
| `core` | required | spaces, channels, identity, sessions |
| `media` | required | avatars and attachments |
| `jobs` | required | deletions, exports, mail, expired-row sweep |
| `voice` | optional | only if voice is wanted, and see §5 about media paths |
| `botapi` | optional | only if the operator runs bots |
| `admin`, `account` | optional | operator and developer consoles |
| `commerce` | off | entitlements and payments have no meaning here |
| `moderation` | off | ONNX image moderation; memory-bound, and off by default |

**Infrastructure.** A database, NATS, a Redis-compatible cache, object storage, and — if voice is on — an
SFU. Each is either ours to run or the operator's to supply, and the wizard asks per item. External object
storage is the common one: somebody with an S3 bucket should not be made to run their own.

## 7. Configuration

Argon already reads layered configuration: the image carries defaults, `conf.d/<feature>.json` carries
the deployment's intent one file per feature, and environment variables win over both. A file may only
carry sections its own feature declared — anything else is reported rather than silently applied.

**The installer writes `conf.d`, and it does not know what goes in it.** The server binary can say:
`--roles` lists roles and topologies, `--explain <role>` lists every feature that role enables *and the
configuration sections each one reads*, and `--validate-config` checks the result and exits non-zero when
it is wrong.

So the bootstrapper asks the binary, generates, and then validates with the same binary. It cannot drift
from the code, because it never had a second copy of that knowledge to drift from.

### Two things the generator always writes

**`Database:Provider`, explicitly.** Self-hosted runs PostgreSQL, so the generator writes `PostgreSql`
and never leaves the key absent: unset or misspelled it resolves to CockroachDB, and the boot path probes
the server and refuses to start on a mismatch. Spell it as the `DatabaseProviderKind` member —
`PostgreSql`; `Postgres` parses to nothing and lands on the same refusal.

**Secrets are not mixed into `conf.d`.** Settings go in the per-feature files; passwords, keys and tokens
go in one separate file with mode `600`. Not for secrecy on a box the operator owns — for replaceability:
when Vault comes back it becomes another configuration layer, and swapping one file for one source is a
change, while combing values out of a dozen files is a project.

---

## 8. Secrets

**No Vault in the first version.** It is optional in the code — `VaultAuthMode.None` registers no client —
and on a single box where the operator is root it protects against nothing: whatever unseals it lives on
the same disk. Its dynamic database credentials are behind a flag that is legacy and unused.

Secrets are generated by the installer, written to one file with mode `600`, and owned by the panel.

**Vault returns later**, as the thing that rotates most of the secrets, and the design above is what makes
that cheap: it slots in as a configuration layer between `conf.d` and the environment. Nothing that reads
a secret has to change.

## 9. Lifecycle

**Start and stop** are compose operations the panel owns.

**Upgrade** is where installers of this kind fail. Argon runs migrations on boot under a lease, and applies
schema declarations after them, so an upgrade is not "swap the image" but "swap the image and survive a
migration".

A failed migration is the safe case: nothing applied, the pod does not start, the database is untouched
and fixing forward is the only option. The case that costs data is a **successful** migration followed by
rolling the image back, because the old build then meets a schema newer than it knows.

Most of the time that is fine, and EF is why: it selects named columns, so a column the old build has
never heard of does not disturb it. The exception is a column that went **away**. `DropColumn` is real —
`Conversations.LastMessageId` was dropped this week — and an old build still asking for it gets `42703` on
the first query that touches that table. EF does not protect against that in either direction; it is the
schema that moved.

**Decided:** dumps are taken on major-version upgrades, not on every one, and operators are expected to
step through versions rather than jump. That is the right trade — a dump before every patch release is a
tax nobody pays attention to, and the destructive migrations are the ones that land on majors anyway.

What the policy still owes: something has to *hold* to it. A patch upgrade that happens to carry a
`DropColumn` breaks the rollback story silently, so the release process — not the installer — is where
that gets caught. Worth a check in CI that a non-major release carries no destructive migration
operation.

## 10. The panel

After setup the same container stops being an installer and becomes a control surface: container state,
logs, configuration, upgrades, backups, certificate expiry.

**It is reached through the ingress, not on a port of its own**, and that is true from the first
second — including during setup, when nothing else exists yet.

This was the other way round in an earlier draft: the bootstrapper held `:443` itself and handed it to
Traefik once setup finished. That handover is a container answering a request while closing the listener
that carried it, and on path C it needs a *second* ACME client in the install script to obtain the
certificate Traefik will then obtain again. Both dissolve if the order is reversed.

So `bootstrap.sh` starts a two-service project — Traefik and the panel — before asking anything beyond
the domain and the traffic shape. Traefik gets the certificate by whichever of §5's paths was chosen and
routes `/` and `/panel` to the panel; the operator reaches the setup UI over real TLS from the
beginning. `apply()` then writes the full compose document over the same project, and compose adds the
roles and the infrastructure and updates the edge in place. There is no moment when the front door is
down, because it is the same container throughout.

The bootstrap document is emitted by the panel image itself — `emit-bootstrap`, run once by the install
script — rather than written by the shell. The project name, the network subnet, the edge's volume and
both Traefik paths have to be identical across the two phases, or the second `compose up` builds a
*second* project beside the first, with the old edge still holding `:443` so the new one can never bind
it. One source of truth for that is `compose.ts`; the script pulls the image anyway.

It holds the docker socket, which is root-equivalent. That is acceptable for a box whose owner is
installing it — but it means the panel is the highest-value target on the machine, and its authentication
must be a real account with a real password by the time setup finishes, not the bootstrap code from §4.

## 11. Two facts about other people's products, checked

Both were stated here as believed and marked to be verified. Both have been, against Cloudflare's own
documentation and endpoints, in August 2026.

**1. The published proxy ranges.** `GET https://api.cloudflare.com/client/v4/ips` answers unauthenticated
with `{ result: { ipv4_cidrs, ipv6_cidrs, etag }, success: true }` — fifteen IPv4 ranges and seven IPv6
ranges as of checking. The human-readable lists are at `cloudflare.com/ips-v4` and `/ips-v6`. Pin the API
URL at build time if detection is ever built; nothing currently consumes it, because the installer asks
the operator which path they are on rather than sniffing for it.

**2. The WebSocket idle timeout.** Cloudflare **does not publish a number.** Its networking documentation
says a connection is closed "when no data is transmitted in either direction for a period of time", that
Enterprise customers can negotiate a custom timeout, and that the answer is a client-side heartbeat.

So the design question this raised cannot be answered by matching the number — only by undercutting it.
Argon's hub sends its own keep-alive, and `ArgonWebSocketOptions.KeepAliveInterval` defaults to **one
minute**, which overrides SignalR's own fifteen seconds. That is probably inside Cloudflare's window and
has little room in it.

The installer therefore writes `WebSockets:KeepAliveInterval` as thirty seconds on the
`cloudflare-proxied` path, and on no other. The cost is one small frame per client per thirty seconds;
what it buys is margin against a number nobody outside Cloudflare knows. The other three shapes have
nothing between the client and the edge that would time a socket out, and a heartbeat they do not need is
traffic on somebody's mobile data.

What this still cannot promise: an Enterprise account with a *shorter* negotiated timeout, or a future
change to the default, would need the interval lowered again. It is a setting in `conf.d`, so that is an
edit rather than a release.
